## Context

See proposal.md (Why) for the symptoms. The constraints that shape the fix:

- The pre-paint script in `index.html` sets `data-theme="dark"` on `<html>`
  before React loads. That happens when the stored mode is Dark, or when
  it is System on a dark device. Afterwards, only `useApplyTheme` removes
  it: `PublicLayout` calls `useApplyTheme('light')`.
- `RouteErrorPage` is the data router's `errorElement`
  (`App.tsx: createBrowserRouter([{ …, errorElement: <RouteErrorPage /> }])`).
  It replaces `RootLayout`, and `RootLayout` holds `ThemeModeProvider`. So
  the error page renders with no provider, and `useApplyTheme` (which
  calls `useThemeMode`) would throw there. Nothing removes `data-theme`,
  and the dark tokens apply.
- `BRAND_LOGOS.light` is `logo-guestify.svg`: a teal mark plus a teal "Gu"
  plus a `#12172A` "estify". On the dark `surface` token, only the teal
  parts are visible. That is the "Gu" in the screenshot.
- `MobileNavBar` in `AppShell.tsx` (themed) also uses `variant="light"`
  on `bg-surface`. It is only `AppShell`'s fallback, though: both
  `AdminLayout` and `StaffLayout` pass their own `AppTopBar` (no logo), so
  no current page renders it. Found during apply.
- Tailwind already has a `dark:` variant keyed to `[data-theme=dark]`
  (`src/styles/index.css`).
- `PortalFooter` today has `py-8 md:py-10`, and on desktop it stacks
  logo, tagline and copyright in a `max-w-[400px]` column. That is about
  180px at 1920px wide.

## Goals / Non-Goals

**Goals:**
- The error page is light in every theme setting, with no provider
  needed.
- No logo can lose its wordmark in the dark theme, on any surface that
  follows the theme.
- One compact footer for all public pages.

**Non-Goals:**
- Theming the error page dark for staff users. The spec keeps all public
  chrome light, and the error page uses the public header and footer.
- Regenerating or editing the logo SVGs (they are generated by
  `VMSS_API/scripts/build_brand_assets.py`).
- Changing the staff login footers (their own components) or the
  sidebar logos (already `on-dark`/`mark`).

## Decisions

### D1. A provider-free "force light" hook for the error page

Add `useForceLightTheme()` to `theme-mode-context.tsx`, next to
`writeTheme`. In a `useLayoutEffect`, it sets `pageScope = 'light'` and
calls `writeTheme('light')`, which removes `data-theme`. It does not read
the context. `RouteErrorPage` calls it. `useApplyTheme` keeps its own
behaviour.

- Why `useLayoutEffect`: the attribute changes before the browser paints
  the error page, so there is no dark flash. This matches `useApplyTheme`.
- Why in `theme-mode-context.tsx`: `writeTheme` and `pageScope` are
  private to that module. Keeping every theme write in one file holds the
  "change both together" contract with `index.html`'s pre-paint script.
- Alternative considered: wrap `RouteErrorPage` in a `ThemeModeProvider`
  and call `useApplyTheme('light')`. Rejected. The error page is the
  "nothing else worked" surface, and its comment says it uses "nothing but
  plain markup". Mounting a provider (with storage and media-query
  listeners) there adds ways for the error page itself to fail.
- Alternative considered: delete the attribute inline in
  `route-error.tsx`. Rejected because it would duplicate `writeTheme`
  outside its module.
- Nothing restores the user's theme when they leave the error page. Its
  only action is a full reload, which re-runs the pre-paint script.

### D2. A theme-following logo variant

Add a `'themed'` variant to `BrandLogoVariant`. `BrandLogo` renders it as
two `<img>` elements:

- the dark-wordmark lockup, with `dark:hidden`;
- the white-wordmark lockup, with `hidden dark:block`.

Both get the same sizing classes and the same alt text. The hidden one is
`display: none`, so assistive technology announces only one logo.

- Use it in `MobileNavBar` (a fallback no layout renders today, so this
  only keeps it correct if one ever does), `PortalHeader` and
  `PortalFooter`. Public pages are forced light, so
  this changes nothing visible there. It is the safety net: if a public
  page ever reaches dark again (another provider-less route, a regression
  in D1), the logo stays readable instead of turning into "Gu".
- Why CSS (`dark:`) and not `useThemeMode()`: CSS works without a
  provider, which `PortalHeader`/`PortalFooter` need on the error page. It
  also follows a live theme switch in the same repaint as every other
  token, with no React re-render.
- Alternative considered: one SVG with `currentColor` for the wordmark.
  Rejected because it means hand-editing generated assets (see Non-Goals).
- Keep `'light'` and `'on-dark'` as they are, for surfaces whose
  background never changes with the theme (the navy staff headers).

### D3. Compact footer layout

`PortalFooter` keeps its content and gets a new layout:

- Padding: `py-4` on phone and tablet, `lg:py-5` on desktop; side padding
  unchanged (`px-4 md:px-12`).
- Brand block: stacked (`gap-1`) below `lg`. From `lg` it becomes one row
  (`lg:flex-row lg:items-center lg:gap-4`): logo, tagline, copyright. The
  `max-w-[400px]` cap goes, because it would force the row to wrap.
- Outer row: unchanged structure. It is brand block left, links right
  from `lg`, and stacked with `gap-3` (was `gap-6`) below.
- Links keep `min-h-10` below `lg` (touch target, responsive-layout
  "Controls Are Touch-Operable") and `lg:min-h-0` above.
- Resulting desktop height: 2 × 20px padding + 28px logo row = 68px,
  under the spec's 88px cap. That leaves room for a 1px border and for
  text line-height rounding.

Alternative considered: drop the tagline to save space. Rejected because
the user asked for a smaller footer, not less content, and the landing
page spec does not need it gone.

## Risks / Trade-offs

- [Desktop row wraps at 1024–1280px when privacy, terms and support are
  all configured and the support email is long] → The links block already
  wraps (`sm:flex-wrap`). The spec caps height only "when its content fits
  on one row", and nothing is clipped. The responsive-matrix e2e checks
  1440px with all links set.
- [Two `<img>` per themed logo double-download the SVG] → Both SVGs are
  small Vite-bundled assets already used elsewhere, and are fetched once
  and cached.
- [A broken *page* chunk never reaches the error page] → Found during
  apply, pre-existing and out of scope: `lazyPage` clears its reload flag
  whenever any lazy chunk loads, and the layout chunk loads fine on each
  reload, so a page chunk that always fails reloads forever. The e2e test
  fails the layout chunk instead. Worth a separate fix.
- [`useForceLightTheme` leaves `pageScope = 'light'`] → It only runs when
  the provider is gone, and the next navigation is a full reload. That
  resets module state.
- [Existing scenario "Footer logo is not stretched" (brand-identity)
  expects a 28px-tall logo] → D3 keeps `h-7`. The themed variant puts the
  sizing classes on both images, so the visible one measures the same.

## Migration Plan

Frontend only. It ships with the normal web deploy, with no API, asset or
environment changes. To roll back, revert the commit.
