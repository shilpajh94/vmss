# File Storage Specification

## Purpose

Defines the behavior any feature relies on when it saves a visitor-supplied
file (ID-proof scan, photo) and later needs to retrieve it, independent of
which physical backend (local disk in dev, S3-compatible object storage in
prod) is actually storing the bytes.

## Requirements

### Requirement: Uploaded file content is validated by real content, not client-declared metadata
The system SHALL determine a file's true type by inspecting its actual
content (magic bytes), never by trusting the client-supplied `Content-Type`
header or the filename extension. Only an explicit allow-list of types
(JPEG, PNG, PDF) SHALL be accepted; anything else is rejected.

#### Scenario: Renamed executable is rejected
- **WHEN** a file whose real content is not one of the allow-listed types is
  uploaded, regardless of its filename or declared content type
- **THEN** the upload is rejected and no file is stored

#### Scenario: Genuine allow-listed file is accepted
- **WHEN** a file whose real content matches JPEG, PNG, or PDF is uploaded
- **THEN** the upload is accepted for storage

### Requirement: Uploaded file size is bounded
The system SHALL reject an uploaded file that exceeds the configured maximum
size for its context before the full content is persisted.

#### Scenario: Oversized file rejected
- **WHEN** an uploaded file's content exceeds the configured maximum size
- **THEN** the upload is rejected with a clear error and nothing is stored

### Requirement: Storage backend is swappable without changing caller behavior
The system SHALL expose file storage as a save/retrieve interface that
returns an opaque storage key, never a raw filesystem path or backend-specific
detail, to its callers. Which physical backend is active (local disk vs. an
S3-compatible object store) SHALL be selected by configuration, and switching
backends SHALL NOT require any change to a calling feature.

#### Scenario: Same caller behavior across backends
- **WHEN** a feature saves a file and later resolves it, regardless of
  which backend is configured
- **THEN** the feature receives an opaque key on save and a usable retrieval
  reference on resolve, with no backend-specific branching in the caller

### Requirement: Storage keys are generated server-side, never from client input
A file's storage key SHALL be generated by the system, incorporating the
owning tenant, and SHALL NOT be derived from a client-supplied filename or
path.

#### Scenario: Client-supplied filename cannot influence the storage path
- **WHEN** a file is uploaded with an unusual or malicious filename (e.g.
  containing path-traversal sequences)
- **THEN** the stored object's key is unaffected by that filename and no
  path outside the intended storage location is written to or read from

### Requirement: The S3-compatible backend persists and retrieves files correctly
When configured to use the S3-compatible backend, the system SHALL persist
an accepted upload to the configured bucket under its generated key, and
SHALL provide a way to retrieve the stored object's content by that key.

#### Scenario: Save then retrieve round-trip
- **WHEN** a file is saved while the S3-compatible backend is active
- **THEN** a subsequent retrieval by the returned key returns the same
  content that was saved

#### Scenario: Backend unreachable or misconfigured
- **WHEN** the configured object-storage backend cannot be reached or is
  misconfigured
- **THEN** the save operation fails explicitly (the request is rejected)
  rather than silently succeeding without actually persisting the file
